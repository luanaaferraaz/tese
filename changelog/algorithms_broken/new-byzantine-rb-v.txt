ALGORITHM TEMPLATE: New Byzantine-Tolerant RBcast Algorithm
1) IDENTIFICATION

Algorithm name: New Byzantine-Tolerant Algorithm Generated by the RB-Learner

Problem type: Reliable Broadcast

Variant tags:

Fault model: Byzantine
Timing model: Asynchronous

2) SYSTEM MODEL

Processes: A static set Π of n processes.

Max faulty: f = 1.

Resilience condition: n ≥ 4 and f = 1, as stated for this generated algorithm.

Channels / communication assumptions: Reliable authenticated message-passing channels. Sender identity is known.

Timing assumptions: Asynchronous.

Additional assumptions: "Neighbours" means all processes except itself. Correct processes count messages from distinct senders.

3) CORRECTNESS PROPERTIES

RB-Validity: If a correct broadcaster broadcasts m, then all correct processes eventually deliver m.

RB-Agreement: If one correct process delivers m, then all correct processes eventually deliver m.

RB-Integrity: A correct process delivers m at most once, and only if m was broadcast.

4) INTERFACE

External operations: RB-Broadcast(m), invoked by the broadcaster.

Output events: DELIVER(m), fired at most once per message.

5) ROLES

Broadcaster: Sends the initial message to neighbours.

Receivers / Relayers: Send support messages to neighbours.

Witnesses: Processes whose <type1, m> messages count as evidence for delivery.

6) LOCAL STATE

Constants:

n: total number of processes.
f = 1: maximum number of Byzantine processes.
f + 1 = 2: delivery and forwarding threshold.

Variables:

delivered: set of delivered messages, initially empty.
sent_type0: whether <type0, m> was already sent, initially false.
sent_type1: whether <type1, m> was already sent, initially false.
received_type0[m]: set of senders of <type0, m>, initially empty.
received_type1[m]: set of senders of <type1, m>, initially empty.

7) MESSAGE TYPES

<type0, m>: initial broadcast message.
<type1, m>: support / confirmation message.

Validation rules:

Count only messages from distinct processes.
Send each message type at most once per m.
Deliver m at most once.

8) INITIALIZATION

delivered ← ∅
sent_type0 ← false
sent_type1 ← false
received_type0[m] ← ∅
received_type1[m] ← ∅

9) PROTOCOL PSEUDOCODE

A) On external invocation:

upon RB-Broadcast(m):
    if not already sent <type0, m>:
        send <type0, m> to neighbours
    stop

B) On message receive:

upon receive(<type0, m>) from pj:
    add pj to received_type0[m]

    if received <type0, m> from at least f + 1 distinct processes
       and not already sent <type1, m>:
        send <type1, m> to neighbours

upon receive(<type1, m>) from pj:
    add pj to received_type1[m]

    if received <type1, m> from at least f + 1 distinct processes
       and not already sent <type1, m>:
        send <type1, m> to neighbours

    if received <type1, m> from at least f + 1 distinct processes
       and m not in delivered:
        delivered ← delivered ∪ {m}
        deliver(m)

    stop

10) DECISION / DELIVERY RULE

Deliver m when <type1, m> has been received from at least f + 1 distinct processes.

For this algorithm, since f = 1, delivery requires 2 distinct <type1, m> messages.

After delivery, add m to delivered.

11) QUORUM / KEY STRUCTURAL ARGUMENT

The key argument is that f + 1 distinct senders cannot all be Byzantine. Since f = 1, receiving 2 matching <type1, m> messages means at least one correct process supported the message.

This algorithm is more efficient than the previous Byzantine algorithm because it sends to neighbours instead of all, avoiding self-sends, and it delivers after f + 1 confirmations instead of (n + f) / 2.

12) INVARIANTS

I1 — Distinct support: Only messages from distinct senders count toward the threshold.

I2 — Byzantine alone cannot decide: One Byzantine process cannot produce f + 1 distinct valid senders.

I3 — Support propagation: Once a correct process sees f + 1 <type1, m> messages, it forwards <type1, m> to neighbours.

I4 — No duplicate delivery: A process delivers m at most once.

I5 — No self-send needed: Sending to neighbours is sufficient because each process already knows its own local actions and does not need to send messages to itself.

13) CORRECTNESS ARGUMENT SKELETON

RB-Validity: If the broadcaster is correct, it sends <type0, m> to neighbours. Correct receivers then send <type1, m> to their neighbours. Since correct support spreads, correct processes eventually receive at least f + 1 <type1, m> messages and deliver.

RB-Agreement: If one correct process delivers m, then it received f + 1 <type1, m> messages. At least one of those came from a correct process. The forwarding rule spreads this support to the other correct processes, allowing them to reach the same delivery threshold.

RB-Integrity: A process delivers only once because of the delivered set. Since f + 1 support is required and only f processes can be Byzantine, a Byzantine process alone cannot force delivery.

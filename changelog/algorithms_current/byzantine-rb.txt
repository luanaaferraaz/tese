Vaz, F., Matos, D., Pardal, M. and Correia, M. "Synthesis of Fault-Tolerant Reliable Broadcast Algorithms With Reinforcement Learning". IEEE Access.
ALGORITHM TEMPLATE: Byzantine-Failure RBcast Algorithm
1) IDENTIFICATION

Algorithm name: Most Efficient RBcast Algorithm for Byzantine-Failure Experiment

Problem type: Reliable Broadcast

Variant tags:

Fault model: Byzantine
Timing model: Asynchronous

2) SYSTEM MODEL

Processes: A static set Π of n processes.

Max faulty: f = 1 in the experiment.

Resilience condition: Evaluated with n = 4, f = 1.

Channels / communication assumptions: Reliable authenticated message-passing channels. Processes can identify the sender of each message.

Timing assumptions: Asynchronous.

Additional assumptions: Byzantine processes may send malicious or inconsistent messages. Correct processes count messages only from distinct senders.

3) CORRECTNESS PROPERTIES

RB-Validity: If a correct broadcaster broadcasts m, then all correct processes eventually deliver m.

RB-Agreement: If one correct process delivers m, then all correct processes eventually deliver m.

RB-Integrity: A correct process delivers m at most once, and only if m was broadcast.

4) INTERFACE

External operations: RB-Broadcast(m), invoked by the broadcaster.

Output events: DELIVER(m), fired at most once per message.

5) ROLES

Broadcaster: Sends the initial <type0, m> message.

Receivers / Echoers: Send <type1, m> after receiving enough evidence.

6) LOCAL STATE

Constants:

n: total number of processes.
f: maximum number of Byzantine processes.
Threshold 1: 1 distinct <type0, m> message.
Threshold 2: f + 1 distinct <type1, m> messages.
Threshold 3: (n + f) / 2 distinct <type1, m> messages.

Variables:

delivered: set of delivered messages, initially empty.
sent_type1: whether <type1, m> was already sent, initially false.
received_type0[m]: set of senders from whom <type0, m> was received.
received_type1[m]: set of senders from whom <type1, m> was received.

7) MESSAGE TYPES

<type0, m>: initial broadcast message.
<type1, m>: support / echo message.

Validation rules:

Count only messages from distinct processes.
Send <type1, m> at most once.
Deliver m at most once.

8) INITIALIZATION

delivered ← ∅
sent_type1 ← false
received_type0[m] ← ∅
received_type1[m] ← ∅

9) PROTOCOL PSEUDOCODE

A) On external invocation:

upon RB-Broadcast(m):
    send <type0, m> to all processes
    stop

B) On message receive:

upon receive(<type0, m>) from pj:
    add pj to received_type0[m]

    if received <type0, m> from at least 1 distinct process
       and not already sent <type1, m>:
        send <type1, m> to all processes
upon receive(<type1, m>) from pj:
    add pj to received_type1[m]

    if received <type1, m> from at least f + 1 distinct processes
       and not already sent <type1, m>:
        send <type1, m> to all processes

    if received <type1, m> from at least (n + f) / 2 distinct processes
       and m not in delivered:
        delivered ← delivered ∪ {m}
        deliver(m)

    stop
10) DECISION / DELIVERY RULE

Deliver m when <type1, m> has been received from at least (n + f) / 2 distinct processes.

After delivery, add m to delivered.

11) QUORUM / KEY STRUCTURAL ARGUMENT

The algorithm uses thresholds to avoid trusting a single process. A Byzantine process alone cannot force delivery because:

- Delivery requires (n + f) / 2 distinct <type1, m> messages. With n = 4, f = 1, this threshold is ceil(2.5) = 3.
- A single Byzantine can contribute at most 1 <type1, m> directly, and can trick at most 1 correct process into sending <type1, m> by forging a <type0, m>. This produces at most 2 distinct <type1, m> messages, which is below the delivery threshold of 3.
- The f + 1 = 2 forwarding threshold ensures that once 2 processes (at least one correct) support m, the support propagates to all correct processes.

12) INVARIANTS

I1 — Distinct sender counting: A process counts at most one message per sender.

I2 — One Byzantine is insufficient: Since at most f processes are Byzantine, f + 1 support messages imply at least one correct supporter.

I3 — Support amplification: If enough processes see <type1, m>, they forward <type1, m> to all.

I4 — No duplicate delivery: A process delivers m at most once.

13) CORRECTNESS ARGUMENT SKELETON

RB-Validity: If the broadcaster is correct, all correct processes eventually receive <type0, m>, send <type1, m>, and eventually collect enough <type1, m> messages to deliver. With n = 4 and f = 1, there are 3 correct processes. Each sends <type1, m>, so every correct process receives at least 3 distinct <type1, m> messages, which meets the (n + f) / 2 = 2.5 (rounded to 3) threshold.

RB-Agreement: If one correct process delivers, it has seen at least (n + f) / 2 distinct <type1, m> messages. Among those, at least one must be from a correct process (since the threshold exceeds f). The forwarding rule using f + 1 ensures that once a correct process sends <type1, m>, it spreads to all correct processes, allowing them to also reach the delivery threshold.

RB-Integrity: A correct process delivers m at most once because of the delivered set check. The "only if m was broadcast" guarantee holds because a Byzantine process alone cannot produce enough support to trigger delivery: with n = 4 and f = 1, delivery requires (n + f) / 2 = 2.5 (rounded up to 3) distinct <type1, m> messages. A single Byzantine can send at most 1 fake <type1, m>, and can trigger at most 1 correct process to echo by sending a fake <type0, m>. That gives 2 total <type1, m> messages (1 Byzantine + 1 tricked correct), which is below the delivery threshold of 3. Therefore, a Byzantine process cannot cause delivery of an unbroadcast message.

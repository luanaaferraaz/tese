ALGORITHM TEMPLATE: Reliable Broadcast (General Omission)
1) IDENTIFICATION

    Algorithm name: Reliable Broadcast — General Omission Variant (RB-GO)

    Problem type: Reliable Broadcast

    Variant tags:

        Fault model: [O] General Omission

        Timing model: [AS] Asynchronous

2) SYSTEM MODEL

    Processes: A static set Π of n processes, {p1, p2, ..., pn}.

    Max faulty: f, where n > 2f (a correct majority is required).

    Resilience condition: n > 2f. Under general omission, a faulty process may fail to send messages (send omission) or fail to receive messages (receive omission). The majority condition ensures that correct processes can always outnumber faulty ones in any communication round, guaranteeing that the relay mechanism propagates messages despite omissions.

    Channels / communication assumptions: Point-to-point links that are reliable between correct processes (eventual delivery, no duplication, no creation). A faulty process may fail to send or receive on any subset of its links.

    Timing assumptions: Asynchronous. No timing bounds on message delivery or processing.

    Additional assumptions: Processes fail only by omission (send or receive). They do not deviate from the protocol logic — they simply may fail to send or receive some messages. Processes cannot detect their own omission failures.

3) CORRECTNESS PROPERTIES

    Validity: If a correct process broadcasts m, then it eventually delivers m.

    No duplication: Every correct process delivers m at most once.

    No creation: If a correct process delivers m, then m was broadcast by some process.

    Agreement: If a correct process delivers m, then every correct process eventually delivers m.

4) INTERFACE (API)

    External operations: rb_broadcast(m)

    Output events: rb_deliver(m)

5) ROLES

    Sender: The process that initiates the broadcast.

    Relayers: All processes (including the sender) that relay messages to ensure delivery despite omissions.

6) LOCAL STATE (per process pi)

Constants:

    n: Total number of processes.

    f: Maximum number of general-omission failures (n > 2f).

Variables:

    delivered: A set of messages already delivered to the application, initially ∅.

    echo_count[m]: For each message m, the number of distinct processes from which pi has received a DATA or RELAY message carrying m. Initially 0.

7) MESSAGE TYPES

    DATA(s, m): Initial broadcast message from sender s carrying content m.

    RELAY(s, m): Relay message forwarded by any process, carrying original sender s and content m.

Validation rules:

    Count only messages from distinct senders (to track how many processes have seen m).

    Check if m is already in the delivered set before delivering.

8) INITIALIZATION

    delivered ← ∅

    echo_count[m] ← 0 for all m

9) PROTOCOL PSEUDOCODE

A) On external invocation:

    on rb_broadcast(m):

        delivered ← delivered ∪ {m}

        rb_deliver(m)

        for every process q ∈ Π:

            send DATA(self, m) to q

B) On message receive:

    on receive DATA(s, m) or RELAY(s, m) from process pk:

        echo_count[m] ← echo_count[m] + 1 (if pk not already counted)

        if echo_count[m] ≥ f+1 and m ∉ delivered:

            delivered ← delivered ∪ {m}

            rb_deliver(m)

            for every process q ∈ Π:

                send RELAY(s, m) to q

        else if m ∉ delivered:

            for every process q ∈ Π:

                send RELAY(s, m) to q

    (Note: Unlike the crash-only variant which delivers on first reception, this variant requires f+1 distinct sources before delivering. This ensures that at least one correct process has vouched for the message, preventing a scenario where only omission-faulty processes propagated a fabricated relay chain.)

10) DECISION / DELIVERY RULE

    Deliver m when:

        The process has received DATA or RELAY messages carrying m from at least f+1 distinct processes (guaranteeing at least one correct source).

    After delivery:

        The message is added to the delivered set to prevent duplicates.

        The message is relayed to all processes to ensure Agreement.

11) QUORUM / KEY STRUCTURAL ARGUMENT

    The f+1 threshold ensures that at least one of the sources is a correct process (since at most f are faulty). Once a correct process relays m, the eager diffusion mechanism ensures all correct processes eventually receive it (since links between correct processes are reliable).

    The majority condition n > 2f ensures that there are at least f+1 correct processes, so if the sender is correct, at least f+1 correct processes will receive and relay the message, allowing all correct processes to reach the f+1 threshold.

12) INVARIANTS

    I1 (Relay propagation): If a correct process pi delivers m, it relays m to all processes. Every correct process eventually receives this relay.

    I2 (Threshold guarantee): If a correct process delivers m, it received m from f+1 distinct processes, at least one of which is correct.

    I3 (Agreement): If any correct process delivers m, eventually all correct processes accumulate f+1 distinct sources for m and deliver it.

13) CORRECTNESS ARGUMENT SKELETON

    Validity:
        If a correct process pi broadcasts m, it self-delivers m immediately and sends DATA to all. Since pi is correct, all correct processes receive DATA(pi, m). Each correct process relays, and since there are at least f+1 correct processes (n > 2f), every correct process eventually accumulates f+1 sources and delivers m.

    No duplication:
        The delivered set explicitly prevents duplicate deliveries. A process checks m ∉ delivered before delivering.

    No creation:
        A process delivers m only after receiving it from f+1 distinct processes, at least one of which is correct. A correct process only sends DATA or RELAY for messages that were actually broadcast (it only relays what it received). The no-creation property of links between correct processes ensures the message chain traces back to the original broadcaster.

    Agreement:
        If a correct process pi delivers m, it received m from f+1 distinct processes and relays m to all. Every correct process eventually receives this relay. Combined with relays from other correct processes that also received m, every correct process eventually accumulates f+1 distinct sources and delivers m. (Follows from I1, I2, I3.)
